HOW IT WAS BUILT

From idea to production in less than three days.

This project is an example of a modern workflow with AI, from an initial idea to a working product in production. I combined the roles of Product Owner, IT Manager and Solution Architect, while OpenAI’s ChatGPT and Codex acted as my engineering team. By defining the requirements, steering the architecture and user experience, and reviewing and testing the implementation, I brought the finished product into production in less than three days.

ChatGPT helped shape the initial ideas, and Codex did most of the implementation work: writing code, configuring AWS resources, connecting services, adding tests, updating documentation and generating architecture diagrams. My role was to steer the project, challenge decisions and test whether the result made sense in practice. Several architectural and UI/UX choices needed that intervention.

My Codex setup includes general instructions requiring automated tests alongside code changes. Some tests are explicitly marked as protected: Codex is instructed to preserve them rather than arbitrarily change their expectations to make an implementation pass. These rules provide a baseline for checking the work, alongside reviewing changes and testing the application myself.

One architectural decision was to use CloudFormation stacks for infrastructure deployment, making the configuration explicit, versioned and repeatable. Another was to choose lower-cost Amazon Nova models rather than retain the initial Claude option, then evaluate the trade-off between cost and answer quality.

I also directed the addition of Bedrock Guardrails and designed the sequence of protections against abusive chat usage. These cover bot verification, origin checks, session authorization, conversation ownership and usage quotas before model invocation. Bedrock Guardrails and grounding instructions then help keep the assistant within its intended scope.

Testing exposed problems that a successful deployment could not reveal. The assistant sometimes claimed that my CV contained no Kubernetes or Docker experience, even though the relevant information was present. Starting with a greeting could change the result of the next question. Increasing retrieval from 10 to 20 source chunks substantially improved the answers—a useful reminder that an AI application depends on the evidence supplied to the model as well as the model itself.

The chat experience also evolved. Requiring registration before the first question introduced too much friction. The revised flow asks for a name and company as the minimum introduction, allows limited guest access, and offers sign-in when a guest allowance is exhausted.

Codex handled most of the detailed implementation work. Human direction, testing and judgment shaped what that work became. The architecture below documents the resulting system.

SYSTEM OVERVIEW

Static at the front. Serverless behind it.

The public pages load independently of the assistant. Authentication, quotas, conversation storage and model inference sit behind a dedicated chat API.

PRESENTATION

A fast static portfolio

HTML, CSS and JavaScript are versioned in GitHub and published through Amplify Hosting. Route 53 provides the website's authoritative DNS; Amplify manages HTTPS and CDN delivery.

APPLICATION

Guest access, verified upgrades

A mandatory introduction and Turnstile establish a guest session. CloudFront and an API Gateway Lambda Authorizer protect chat; Cognito optionally upgrades the same conversation.

KNOWLEDGE & STATE

Evidence and conversation

A reviewed text CV feeds a Bedrock Knowledge Base backed by S3 Vectors. DynamoDB stores quota state and conversation history in separate tables.

These views describe the implementation in aws/amplify.yaml and amplify.yml. They are logical architecture diagrams, rather than a live health dashboard. AWS services use the official AWS Architecture Icons (July 2026 release).

01 / DEPLOYMENT ARCHITECTURE

Two paths from source to production.

CloudFormation manages the infrastructure through an explicit deployment. Amplify automatically builds and publishes application changes pushed to the connected GitHub branch.

  1. Provision the platform

    The local AWS CLI uploads the infrastructure template to private S3 and submits a CloudFormation change set. The stack defines hosting, DNS, IAM, identity, API services, storage and the knowledge base. Secrets Manager supplies the GitHub connection token, private origin token, IP HMAC key and externally configured Turnstile secret. The public Turnstile site key is separate. Session Lambda, Lambda Authorizer, IAM, routes and tracking use the same CloudFormation stack.

  2. Build from GitHub

    A push to the production branch starts an Amplify build. The build assembles the static pages and assets, fetches official App Store artwork and writes the public API and Cognito configuration supplied by the stack.

  3. Prepare the knowledge

    The publisher uploads changed CV text to the private source bucket. Bedrock ingestion splits it into chunks and uses Titan Text Embeddings v2 to populate the separate S3 vector bucket and index. This is indexing for retrieval, rather than model training.

  4. Publish a coherent release

    The build waits for successful knowledge-base ingestion before publishing the site. The connected branch rebuilds automatically; changes to the CloudFormation template require a separate infrastructure deployment.

02 / RUNTIME ARCHITECTURE

From a visitor's question to a grounded answer.

The static website and chat API have separate delivery paths. The application runs primarily in Ireland (eu-west-1); Nova Pro uses an EU cross-Region inference profile.

  1. Introduce yourself and establish a guest session

    The existing greeting is followed by required Name and Company fields. These are self-declared, not verified identity. Start chatting submits the introduction and a Managed Turnstile token through CloudFront to POST /chat/session. A lightweight Session Lambda checks the input, security token and creation-abuse limits before creating a conversation summary and issuing an opaque session credential. It never invokes Bedrock.

  2. Authorize the session and enforce allowances

    Every POST /chat carries the session and backend-issued visitor credentials. CloudFront overwrites the trusted viewer-IP header and adds its private origin token. API Gateway invokes an uncached Lambda Authorizer to check expiry, revocation, visitor binding and conversation ownership. Chat Lambda receives verified context, checks lifecycle and atomically reserves all applicable DynamoDB quotas before inference.

  3. Retrieve evidence and save the exchange

    Bedrock Knowledge Bases retrieves CV evidence from S3 Vectors for Amazon Nova Pro. Every generation retains the numbered Guardrail, denied-topic and prompt-attack filters. Name and company are untrusted context and cannot override grounding. Questions, answers, timestamps and introduction metadata are stored in retained history; a blocked answer is replaced by the fixed scope refusal. Five minutes of inactivity or explicit closure ends the conversation.

  4. Optionally sign in and continue

    A guest allowance triggers Sign in / Register and Maybe later. Cognito keeps its verified-email and optional social-provider flows. POST /chat/session/upgrade uses the existing JWT authorizer and verifies the guest credential before attaching the account and rotating the chat token. Name, company, transcript and pending question are preserved. Authenticated quotas replace guest/IP quotas; global exhaustion never suggests sign-in. Signing out returns to guest mode.

  5. Notify the owner once the conversation starts

    The first saved question and answer atomically add a first-interaction marker and first question to the summary. DynamoDB Streams passes that initial transition to a notification Lambda, which publishes to an SNS email subscription. The message contains the self-declared introduction, first question, time and verified email when already authenticated. Later messages, account upgrades and closure do not create another notification event. Leased publication records suppress ordinary retry duplicates; email delivery remains at least once. Notification failures do not block chat replies.

03 / DATA, SECURITY & OPERATIONS

Clear boundaries. Bounded model use.

The design separates public content, identity, persistent quota counters and retained conversation data. AWS managed services provide the platform without a dedicated VPC or application servers.

API PERIMETER

Layers of verification

CloudFront checks request shape, API Gateway validates established sessions, and Lambda verifies the origin token and ownership. CORS is a browser restriction; authentication is enforced separately. API responses are not cached.

COST CONTROL

Limits before inference

Visitor, IP, user and global allowances are consumed atomically before Bedrock runs. API throttling and a 600-token answer limit further bound model use. These controls do not impose a hard cap on total AWS charges; the site has no WAF web ACL.

MODEL BOUNDARY

Reviewed knowledge first

The model receives retrieved CV evidence, the question and the self-declared name and company. A strict scope prompt and versioned Bedrock Guardrails help keep replies on topic. Guardrails and grounding reduce unwanted responses but do not guarantee perfect classification or accuracy. The recruiter-specific CV tool remains a demonstration.
